# 인수인계: 공장 프로필 + 라인 전체 3D + 상태 데모 (2026-10-08)

## 한 줄 요약
설비·치수·연결·사이클을 한 파일(`contracts/examples/factory_profile.line_a.json`)에서 읽어 검증, 2D 배치도, 3D, 데모 데이터를 만든다. 이 위에 설비 35대 전체에 대한 **데모 상태(정상·주의·이상) 주입**을 `/lab/plant`에 얹었다. 상태는 전부 더미이고 실제 설비 데이터가 아니다.

## 실행
```bash
cd frontend/web-admin && npm run dev      # http://localhost:3000/lab/plant  (라인 전체 3D + 상태 주입)
node scripts/check-factory-profile.mjs    # 프로필 검증 (스키마·참조·공급-수요·겹침·택트·병목). 경고 2건은 의도
node scripts/render-layout.mjs            # docs/plant-layout-draft.svg 재생성
```
프로필 JSON은 `scratchpad/gen_profile.py`로 생성했지만 이 파일은 레포 밖(세션 임시 폴더)이다. 이후 수정은 JSON을 직접 고치고 `check-factory-profile`로 검증하면 된다.

## 보기 팁
- `/lab/plant?focus=<설비 id>` (예: `laser_01`, `press_01`, `washer_01`)로 해당 설비 앞에서 시작. 좌하단 "종류로 색칠"이 가장 차분한 외형, 기본은 치수 근거 색.
- 로봇·컨베이어 포함 모든 설비에 디테일 외형 적용.

## 상태 데모 동작
- 설비 클릭 → 카드의 "상태 (데모)"에서 시나리오 버튼으로 주입, 같은 버튼 다시 누르거나 "복구"로 해제, 좌하단 "초기화"로 전체 해제.
- 시나리오는 유형별 2개(주의/이상). 표에 없는 유형은 과열 경고/정지 알람.
- **전파 규칙**(`plantStatus.ts`): 이상 상태인 공급원이 `effectiveEdges`로 이어진 하류를 만든다. 전원 공급원이 이상이면 하류는 이상(정지), 냉각·압축공기·가스·집진이 이상이면 하류는 주의. 전파된 설비는 카드에 "○○의 ○○ → ○○ 공급 영향"으로 원인이 표시된다. 연결이 "확인 필요"면 "(연결 확인 필요)"가 붙는다.
- 확인한 예: 칠러 "냉각수 유량 저하" → 칠러 이상 1 + 레이저·용접 전원·로봇 01~03 주의 5. 전원반 "메인 차단기 트립" → 이상 23 / 주의 2 / 정상 8.

## 센서 → 규칙 엔진 → 이벤트 (메인 앱)
- 메인 앱 `AdminShell`이 1초마다 로봇 3대의 센서를 읽음(`sensorMonitor.ts`). 값은 라인에 주입된 고장(`plantState.ts`, `/lab/plant`와 공유)에서 만들어짐. 주입 탭의 "센서 경로 주입"으로도 걸 수 있음.
- 센서가 정상 범위를 벗어나 상황이 바뀌면 `runDetection()`(규칙 엔진을 부르는 **유일한 곳**, 수동 주입도 같은 함수)이 불려 이벤트 "센서 경보 · …"와 "Rule Engine · 1위 …", 이력 행(시나리오 "센서 자동 감지", 강도 "자동", 감지 근거), 상태 칩 반영. 정상으로 돌아오면 "센서 정상 복귀"와 함께 자동 복귀. 이상 공급원(칠러, 전원반 등)이 있으면 "공급 연결: …" 이벤트를 덧붙임.
- 수동 주입이 걸린 로봇은 초기화 전까지 센서 감시가 건드리지 않음(주입 탭 결과는 그대로). 초기화는 센서 경로 고장도 같이 지움.
- **규칙 엔진에 규칙 2개를 더함(기존 결과는 그대로)**: 온도만 오르고 진동·전류 변화가 없으면 냉각라인 0.60(주의), 전류와 진동이 둘 다 -80% 이하면 전원 공급 중단 0.75(이상). 기존 주입 6가지(약·중·강 × 2시나리오)는 전후 결과가 완전히 같음을 확인.
- 확인한 것: 칠러 유량 저하 → 로봇 3대 냉각라인 0.60(주의), 전원반 차단기 트립 → 로봇 3대 전원 공급 중단 0.75(이상), 베어링 마모 → 0.78, 모터 과부하 → 0.70(플랜트 상태와 같은 단계), 고장을 풀면 정상 복귀.
- 한계: 센서가 로봇 3대에만 연결됨(엔진이 로봇 기준). 센서 경보의 이상 점수(0.55 / 0.91)는 가정. 메인 앱엔 흐름 시뮬레이션이 없어 로봇이 항상 작업 중이라고 가정.

## 메인 앱 지도 = `/lab/plant` 장면
- 메인 앱 지도 탭은 이제 `PlantOverview`(`/lab/plant`와 같은 코드)를 `main` 바인딩으로 씀: 선택은 앱이 소유(`selectedId/onSelect`), 로봇 판정은 Rule Engine 상태(`robotStatus`)와 플랜트 상태 중 더 나쁜 쪽, 로봇을 고르면 앱의 상세 카드(Advisor), 나머지 설비는 `/lab/plant`의 카드(센서·시나리오 주입·연결·출처). 색은 `/lab/plant`와 같게 기본 "치수 근거로 색칠"(초록 직접 확인·노랑 보조 출처·회색 가정), 하단에서 "종류로 색칠"·"단색"으로 전환. 주의·이상 설비는 상태색 + 발광 + "!" 라벨이라 근거 색과 구분됨(주의 노랑과 보조 출처 노랑이 비슷하니 "!" 라벨을 기준으로 볼 것). 연구용 HUD(제목, 치수 근거 색칠·범례, 상태 줄)는 숨김. 다른 탭이 지도를 덮으면 HUD 숨김.
- 이전 중립 지도(`FactoryMap`)는 지우지 않았고 `/?map=classic`으로 볼 수 있음.
- 확인한 것: 칠러 고장 → 칩 주의 5·이상 1, 지도 "!" 라벨 6개(같은 수), 로봇 03 선택 시 앱 상세 카드·Advisor 버튼, 이력 탭 전환 시 HUD 숨김·복귀. 안 한 것: 로봇 카드에 센서 패널 없음(로봇은 앱 카드를 씀), 카메라 초기 위치를 상단 바에 맞춰 조정하지 않음, 터치·작은 화면.

## 문제 보고 (상단 바 "문제 보고", `lib/bugReport.ts`)
- 이상한 동작을 봤을 때 누르면 재현용 JSON 파일(`kfc-report-날짜-시각.json`)을 내려받음. **어디에도 전송하지 않음**(서버 수집은 2단계, Notion 계획).
- 내용: 시각·URL·브라우저·화면 크기·GPU, 탭·선택·칩·주입된 고장, 설비 상태와 센서 변화, 최근 이벤트 30개·이력 20건(원인 후보, 해결 여부, 조치), localStorage 키 2개, 최근 오류 50개(`error`·`unhandledrejection`·`console.error`·WebGL 컨텍스트 손실), 최근 클릭 40개(버튼 이름만, 입력값은 기록하지 않음). NaN·Infinity는 null로 씀.
- 화면이 죽을 때는 `app/error.tsx`가 "다시 시도"와 "문제 보고 파일 받기"를 보여 줌.
- 확인한 것: 오류와 console.error를 일부러 낸 뒤 파일에 들어가는지, 탭·주입 상태·이력·클릭 기록·GPU 정보 확인. 안 한 것: `error.tsx` 화면을 실제로 띄워 보지 않음(빌드만 통과), 전역 오류(`global-error`)는 만들지 않음.

## 이송물과 가공물 (`workpieces.ts`, `Carriers`)
- 이송물은 회색 플라스틱 트레이이고, 그 위에 **단계별로 모양이 바뀌는 가공물**이 올라감(가정한 브래킷): 0 원자재 강판 더미 → 1 레이저 절단 블랭크(구멍) → 2 ㄱ자로 구부러진 브래킷 → 3 디버링·세척(밝은 색) → 4 가공(구멍 뚫림) → 5 용접한 한 쌍(용접선) → 6 검사 합격 표시 → 7 각인. 갈색 카톤은 **포장 단계 이후**에만 나옴(그전에는 없음).
- 단계는 `stageOf(token)`: 이동 중에는 마지막 설비가 만든 모양, 설비 안에서는 사이클 절반에서 바뀜(레이저가 절반 돌면 절단된 모양). 토큰에 `src`(어느 설비에서 왔는지) 추가. 단계마다 합쳐진 메쉬 하나(정점 색)라서 이송물 하나당 그리는 호출은 트레이·가공물·카톤 3개.
- 개발 확인용: 주소에 `?debug`를 붙이면 콘솔에서 `window.__kfc.sim`(시뮬레이션)과 `window.__kfc.cam`(`pose`, `at`, `focus`)을 쓸 수 있음. 일반 사용에는 영향 없음.
- 확인한 것: 단계 0, 1, 4, 5를 3100에서 해당 위치로 카메라를 보내 확인(`.kf-shots/A/`, git 제외). 안 한 것: 설비 안에서 모양이 바뀌는 순간, 불량 경로(검사 → 격리함), 포장 이후의 출하, 단계 2·3·6·7 눈으로 확인.

## 로봇 작업과 타이밍 (`PlantOverview`의 `Robot`·`workPoint`, `plantSim.ts`)
- **로봇은 공구를 들고 있고 부품을 집지 않음**(01 가공 스핀들, 02 검사 스캐너, 03 용접 토치). 부품은 지그 위 트레이에 고정되어 있고 공구가 부품 위 실제 작업 지점으로 감: 가공은 구멍 4곳을 차례로(내려가 칩이 튐), 검사는 트레이 위를 훑으며 빔 켬, 용접은 두 이음선을 따라 불꽃(오렌지 입자)을 냄. 작업 지점은 트레이 좌표(`workpieces.ts` 기준)에서 계산해 도착한 트레이의 실제 위치·방향을 따라감. 공구 끝은 목표를 부드럽게 따라가고, 설비가 쉬면 처음 자세로 돌아감. 집기·놓기(핸들링)는 이 라인의 로봇 역할(가공·검사·용접)이 아니라서 만들지 않음.
- **높이**: 지그 위치의 트레이가 벨트 아래(0.45 m)로 묻히던 문제를 고침(벨트 위 0.73 m). 2스테이션 포지셔너는 작업대가 벨트보다 0.4 m 높아 트레이를 1.11 m로 올림(포지셔너 중앙 기둥 위). 높이 변화는 틱마다 부드럽게(`glideTo`, `restOf`).
- **타이밍**: 설비의 `busy/state/progress`를 틱 끝에 다시 맞춤(`syncActs`). 전에는 부품이 들어오고 나가는 순간 한 틱(0.05초) 늦게 바뀌었음. 모양이 바뀌는 시점은 사이클 중간이 아니라 작업이 끝날 때(`CHANGE_AT`: 레이저 0.85, 프레스 0.9, 가공 0.9, 용접 0.92, 검사·마킹·포장 0.9, 디버링·세척 0.5(안이 가려져 있음)).
- **검증(브라우저 `?debug`, 시뮬레이션을 직접 24,000틱 진행)**: 설비 11곳 모두에서 "가동 중인데 부품 없음", "부품 있는데 가동 안 함", 진행률 불일치 0건. 평균 가공 시간은 사이클 값과 한 틱 이내로 일치(레이저 6.15 s 대 6.11, 프레스 23 대 22.96, 디버링 10 대 10, 세척 18.05 대 18, 가공 7.6 대 7.56, 검사 8.55 대 8.5, 포지셔너 12.05 대 12, 최종 검사 4.9, 마킹 6.05 대 6, 포장 6.25 대 6.2). 안 한 것: 설비 동작(램, 레이저 시트 등) 애니메이션이 `progress`와 육안으로 맞는지 모든 설비에서 확인, 30×·60× 빠른 배속에서의 화면 지연, 불량 경로.

## 제조사 문서로 맞춘 치수 (로봇과 설비)

- **레이저·프레스 브레이크에 이송물이 들어감**: 두 설비의 이송물 위치는 `data/machinePaths.ts`의 한 곳에서 계산하고, 시뮬레이션(토큰)과 3D 모양(`MachineDetail.tsx`)이 같은 값을 쓴다. 레이저는 앞의 경사로를 따라 이송물이 올라가 판재 위에 놓이고(0~18%), 판재가 출입구로 셀 안에 들어가(18~32%) 절단(34~66%)한 뒤 나와(68~82%) 경사로로 내려온다(82~100%). 셀은 속이 빈 상자에 판재 높이의 출입구(폭 1.75 m)를 냈고 안에 절단 헤드와 빔이 있다. 프레스 브레이크는 이송물이 앞쪽 입고대에서 펀치 아래 다이 위로 들어가(0~15%) 두 번 굽히고 나온다(85~100%). 램 행정은 펀치 끝이 부품 윗면에 닿게 맞췄고, 다이와 침범하던 것(전에는 8 cm)을 고침. 레이저 입출고 포트를 앞쪽으로 0.5 m 옮겼다(프로필 `flow`의 경로 3개: 끝점 8.5 → 9.0). 이송물을 카트에서 설비의 입고대로 넘기는 것으로 단순화해 포트에서 카트는 사라진다. 클래식 지도(`/?map=classic`)는 설비 안으로 들어가는 모양이 없어 이송물이 상자 속을 지나가는 것처럼 보일 수 있음.
- **처리 중인 이송물 위치는 매 틱 갱신**(`plantSim.ts`의 `place`): 디버링·세척기의 통과 이동이 처음에는 갱신되지 않던 것을 같이 고침.
- **입고 재고 순환(입고 재고가 줄고 트럭이 채움)**은 프로젝트를 물류로 확장할 때 쓰기로 해 지금은 만들지 않음. 입고 재고는 무한 공급으로 둔다.

## 상세 로봇 모델 시험 (GLB, 로봇 01만)

- 다른 AI가 만든 `public/models/robot-detailed/robot-detailed.glb`(2.2 MB, 삼각형 약 5만 개, 근거는 같은 폴더의 `EVIDENCE.md`와 `verification.json`)를 `GlbArm.tsx`로 불러와 **로봇 01**에만 적용했다. 나머지 로봇은 직접 만든 도형 팔 그대로(`robot_01` 하드코딩은 시험용).
- 이 모델은 **제조사 CAD를 쓰지 않은 예시 외장**이다. 제조사 CAD를 받아 보았으나 상업·비공개 웹앱에서 변환·배포해도 된다는 허가를 찾지 못해 쓰지 않았다고 `EVIDENCE.md`에 적혀 있다. 치수 근거는 ABB 사양서 3HAC085909-001 Rev K 16쪽(베이스 676 × 511, 하부 팔 0.9 m, 어깨 앞 오프셋 0.15 m, 상부 0.786 m).
- 관절 연결(노드 메타데이터의 축 정보 사용): j1은 Y, j2·j3·j5는 X, j4·j6은 Z 축. 모델의 관절 영점은 하부 팔이 수직이고 상부 팔이 앞(+Z)으로 수평이며 손목 중심이 팔꿈치 축보다 0.15 m 위다. 우리 IK 각도와의 대응: j1 = q1, j2 = q2, j3 = q3 − atan2(0.786, 0.15), j5 = q5 − (π/2 − atan2(0.786, 0.15)), j4와 j6은 q4, q6. IK 치수는 `GLB_ARM`(A 0.9, B 0.8002, 어깨 높이 0.745 = 받침대 0.3 + 0.445, 손목 중심에서 공구 끝까지 0.342).
- 검증: 이 대응으로 IK 목표 4곳을 순운동학으로 다시 계산해 위치 오차 0, 공구 축이 정확히 아래임을 확인. 가공 중 로봇 01의 관절각은 J2 0~52°, J3 −49~0°, J5 81~90°로 데이터시트 범위 안. 화면으로도 공구가 부품 위에 내려가는 것을 확인.
- 아직: 도달이 끝점까지 전부 맞는지는 로봇 01의 가공 한 주기만 봄. 회전 부호와 영점은 모델 쪽 `extras`에 "미검증"으로 적혀 있어 시각으로만 맞췄다. 공구 장착 기준점(TCP) 노드는 모델에 없어 `j6`의 면에서 0.045 m 위치에 직접 달았다. 케이블은 모델 자체의 보호관만 있다.

## 공장 로봇 외형 컨셉 (GLB, 로봇 01~03 모두, 2026-10-15)

- 실시간 3D팀 인계본 `public/models/factory-robot-concept/factory-robot-concept.glb`(1.7 MB, 삼각형 30,008개, 메시 50개 + `EXT_mesh_gpu_instancing` 11개 = 볼트 64개, 재질 3종 neutral_paint·machined_metal·neutral_polymer)를 **세 로봇 모두**에 적용했다(`GlbArm.tsx`의 `CONCEPT_MODEL`). 이전 `robot-detailed` 모델은 `?robot=detailed`로 비교용으로 남겼다. 근거는 같은 폴더의 `EVIDENCE.md`·`verification.json`·`HANDOFF-README.md`: 모든 형상은 추정(예시)이고 제조사 CAD·사진·로고를 쓰지 않았으며, 가동 한계·충돌·정격은 미검증이다.
- 관절: j1 Y, j2·j3·j5 X, j4·j6 Z. 영점에서 j2 (0, 0.41, 0.11), 하부 팔은 j2→j3 (0, 0.75, −0.14)(뒤로 10.6° 기울어 길이 0.763), 상부는 j3에서 손목 중심(j5)까지 (0, 0.09, 0.635)(위로 8.1° 기울어 길이 0.641), 공구 면은 j5에서 0.138 m. 우리 IK(두 링크 각도를 수직에서 잼)와의 대응: j2 = q2 − zeroA, j3 = q3 + zeroA − zeroB, j5 = q5 − (π/2 − zeroB) (zeroA = atan2(−0.14, 0.75), zeroB = atan2(0.635, 0.09)). 이전 모델은 zeroA = 0이라 같은 식이 된다.
- **표시 크기 1.3배(가정)**: 이 모델은 팔 길이 합이 1.40 m라, 셀이 짜인 로봇↔작업 위치 1.8 m에 닿지 않는다. 그래서 모델을 1.3배로 그리고(합 1.82 m, 프로필 풋프린트는 그대로) 같은 0.3 m 받침대 위에 세웠다. 공구 머리는 1/1.3로 되돌려 크기를 그대로 둠. 1.3배를 쓰지 않으려면 로봇을 작업 위치 가까이로 옮겨야 한다.
- 확인: 인계 ZIP의 SHA256(GLB) 일치, 노드 j1~j6과 축, `GLTFLoader`가 인스턴싱을 복제 후에도 보존(11개·64개), 로봇 3대 모두 공구가 부품 위에 내려가고(스핀들·토치·스캐너), 작업 구간에서 팔이 닿지 못한 프레임 0(관측 프레임 160, 한 가공 주기보다 짧음), 로봇 03이 포지셔너 입구 판을 용접. 삼각형 약 3만 × 3대 ≈ 9.1만, 그리기 호출은 로봇당 약 66.
- **v2 (후면 커넥터 패널)**: 베이스 커넥터 패널이 정면에서 후면(−Z)으로 옮겨진 `rear-panel-v2`(`?v=rear-panel-v2`로 캐시 갱신). 정면에는 패널이 없고 후면에 커넥터 3개(+X 쪽 / 가운데 / −X 쪽)가 있다. 로봇에 닿는 선은 이 커넥터 끝에서 끝나게 그린다(`GlbArm.tsx`의 `robotConnector`, `PlantOverview.tsx`의 `robotLinePoints`): 컨트롤러 케이블 묶음은 가운데, 용접 묶음은 +X, 냉각수는 −X, 압축공기는 +X(용접 묶음이 있는 로봇 03은 −X). 커넥터의 실제 용도·핀 규격은 미지정이라 위 배정은 우리 가정이다. 이전 모델(`?robot=detailed`)은 커넥터가 없어 예전 끝점을 쓴다.
- 못 한 것: 실제 GPU에서의 프레임 속도(검증은 소프트웨어 렌더라 3.7 fps로 의미 없음), 태블릿·낮은 사양, 전체 구간에서의 도달·간섭, 사실감 모드 끈 상태의 재질 비교, 팔 안쪽을 지나가는 걷기 카메라. 공구 장착 기준점은 모델에 없어 j6에서 0.04 m 앞 면에 직접 달았다.

## 표면 질감 (`surfaces.ts`, HUD "질감" 체크)
- 외부 이미지 없이 코드(캔버스)로 그린 회색조 질감 3종을 설비 재질에 **곱함**: `paint`(도장 패널: 0.6 m 이음선, 나사, 가장자리 어두워짐, 타일 1.2 m), `steel`(솔질한 금속, 0.8 m), `dark`(거친 검정 도장, 0.5 m). 몸체 색(근거 등급·상태색)은 그대로 남고 표면만 구조가 생김.

- HUD "질감" 체크로 켜고 끔(재질을 다시 만들도록 `key`를 바꿈). 확인: 프레스 브레이크 1·2 켬/끔 비교(끔은 단색 초록, 켬은 패널 이음선·솔질 빔), 디버링, 전체 화면. 안 한 것: 설비별 환기구 격자·안전 줄무늬·명판 같은 개별 디테일, 태블릿 성능 측정(프래그먼트당 텍스처 3번 읽음), 모든 설비를 하나씩 확대해서 눈으로 확인.
- 검증 방법: 브라우저 패널이 가려져 있어도 `/qa-frame`(404) 위에 같은 출처 iframe으로 열면 3D가 돌아감(메모리 참고).

## 디테일 단계(LOD)와 "예시 모양" 표시 (`PlantOverview`)
- **(2026-10-13 변경)** 상세 모양이 **기본**임: `DETAIL_ALWAYS`(설비 80대 이하)이면 어떤 거리에서도 상세 모양. 단순 박스는 설비가 80대를 넘어 장면이 커졌을 때만 멀리서(`45 m + 큰 변`) 쓰고, 이때 박스에도 받침과 윗면 홈을 달아 약간의 구조를 보여 줌. 현재 36대라 박스는 나오지 않음. "예시 모양" 표시는 가까이(`10 m + 큰 변/2`)·선택·호버일 때만.
- (이전 방식, 사용자가 사진을 본 뒤 바꿈) 디테일 모델은 가까이 볼 때만 나왔음 — 위 항목이 대체함.
- 상세 모양이 보이는 설비 위에 "예시 모양 · 가정"과 **현재 상태**(정상·주의·이상) 표시(`ModelTag`)가 붙고 상태가 바뀌면 바로 따라 바뀜. 설비 카드에도 "상세 모양은 예시(가정)예요. 크기·위치의 근거는 아래 표시를 따르고 상태는 실시간 반영" 안내.
- **훈련에서 새던 것**: 상세 모델의 신호등이 고장 난 설비만 빨갛게 깜빡였음(원인 설비가 바로 드러남). 훈련 제출 전에는 멈춘 설비와 느려진 설비가 같은 호박색 신호등으로 보이고, 모델 표시도 "점검 필요"로만 나옴(`masked`). 움직임(설비가 서고 흐름이 막힘)은 실제 결과라서 그대로 둠.
- **상세 모양 보강(Sonnet 작업, 내가 화면 확인)**: 가스 매니폴드는 프레임 안에 가스 용기 6개씩 두 줄(아르곤 초록·CO2 회색), 체인, 헤더 관, 압력계, 신호등. 집진기는 본체·문·손잡이·호퍼와 수집 드럼·흡입 덕트·상부 배기구·팬 스테이션. 컴프레서는 위로 올라오는 노란 관이 닿을 단자함을 추가. 노란 관은 모델이 아니라 전원 연결선 오버레이(`drop_offset_m` x -0.3)라서, 오버레이가 모델 위에 닿도록 단자함 위치를 맞춘 것이므로 `drop_offset_m`을 바꾸면 다시 맞춰야 함. 모양은 모두 예시(가정).
- **이름표 호버 안정화**: 이름표를 올리면 다른 이름표가 이리저리 바뀌던 문제 수정. 원인은 (1) 호버한 이름표를 자리 배정 우선순위 맨 앞으로 올림, (2) 호버 때 부제가 붙어 이름표가 길어짐, (3) 호버한 설비의 "가정" 연결 태그가 이름표보다 먼저 자리를 차지. 이제 호버는 배정 순서에 관여하지 않고, 부제는 이름표 아래 툴팁(폭 불변), 연결 태그는 이름표 뒤 순위. 확인: 수정 전 호버 1번에 다른 이름표 6개 이동, 수정 후 7개 설비에서 0개 이동·떼면 원상 복귀.
- **표시 겹침 정리**: "예시 모양 · 가정" 표시를 카드·HUD·이름표 뒤로 보냄(`zIndexRange [0,0]`). 표시는 선택·호버한 설비 또는 가까운 거리(상세가 열리는 거리의 절반 이내)일 때만 나옴(`useNear`가 0/1/2 단계를 돌려줌).
- **훈련 카드의 상태 글자**: 제출 전에는 센서 패널 머리의 요약(주의/이상)을 "점검 필요"로 통일(`SensorPanel`의 `hideLevel`). 센서 값과 띠 색은 관측 증거라 그대로 둠.
- 확인한 것: `/lab/plant` 멀리서는 박스, 레이저 절단기 확대 시 상세 모양과 표시(정상), 메인 앱 훈련 칠러 문제에서 확대한 레이저에 "점검 필요" 표시. 안 한 것: 모든 설비 종류의 문턱 거리 눈으로 확인, 성능 측정, 주변 설비 표시가 겹치는 정도 조정, 로봇 팔 모양 자체를 단순화하지 않음.

## 지도 확대 (`PlantOverview`의 `CamApi`)
- **확대 비율 표시**: HUD의 `+ −` 사이에 "거리 % · 배율"(`100% · ×1.0`). 100%는 처음 화면의 카메라 거리(`HOME_DIST`)이고, 확대할수록 작아지며(50% = 절반 거리, ×2.0) 축소할수록 커짐(최대 약 175%). 프레임마다 갱신(창이 가려지면 멈춤).
- 휠 확대는 커서 위치로 들어감(`zoomToCursor`), 최소 거리 6 → 3 m. 하단 왼쪽 첫 줄에 `+` `−` `전체 보기` `선택 설비 확대`. 선택 설비 확대는 보던 각도를 유지한 채 그 설비로 0.7초 동안 날아가고(크기에 맞춘 거리), 설비·이름표를 더블클릭해도 같음. 사용자가 마우스로 돌리기 시작하면 이동이 멈춤.
- 확인한 것: 로봇 03 선택 → 선택 설비 확대로 로봇 팔 모양이 보이는 거리까지 접근, 전체 보기로 복귀, `+` 두 번으로 확대. 안 한 것: 실제 마우스 더블클릭(자동화 환경 한계로 버튼 경로만 확인), 터치 핀치.

- **보기 방식 (좌하단 "보기 방식")**: `궤도`(기본, 예전과 같음: 왼쪽 드래그 = 회전, 오른쪽 드래그 = 이동), `이동`(지도식: 왼쪽 드래그 = 바닥을 따라 이동, 오른쪽 드래그 = 회전, 휠 = 커서 쪽 확대, W A S D · 방향키 = 이동, Shift = 빠르게), `걷기`(1인칭: 눈높이 1.6 m에서 W A S D로 걷고 드래그로 둘러보고 휠로 앞뒤, Q E = 높이, 방향키 좌우 = 회전, Shift = 빠르게, Esc = 궤도로 돌아가기). 건물 밖으로는 2 m까지만 나간다. 걷기 중에 "전체 보기" 같은 HUD 버튼을 누르면 먼저 궤도로 돌아가고 한 번 더 눌러야 움직인다. 터치는 이동 모드에서 한 손가락이 이동, 두 손가락이 확대·회전(걷기는 터치를 지원하지 않음, 드래그 둘러보기만 포인터로 동작).

## 사건 이력 (이력 탭)
- 이력 행 하나가 **사건 하나**. 스냅샷(delta·후보·score)은 감지 때 그대로 두고, 그 뒤 진행만 덧붙임(`HistoryEntry.advisorAt / actionsDone / resolution`): 감지 → 판정 → AI 설명 → 조치 → 해결. 이력 상세 맨 위에 타임라인, 그 아래 권장 조치 체크리스트(Rule Engine 1위 후보의 `recommendedActions`).
- 해결되는 방법(`Resolution.how`): `sensor`(센서가 정상 범위로 돌아와 자동), `manual`(수동 주입 사건에서 "해결 처리" → 장비 정상 복귀), `replaced`(같은 장비에 새 감지가 와서 대체), `reset`(초기화), `restart`(앱을 다시 열 때 — 장비 상태는 저장하지 않으므로 열려 있던 사건을 닫음).
- 센서 경보 사건의 "해결 처리"는 장비 상태를 직접 바꾸지 않고, 원인이 되는 고장(자기 자신 또는 `cause.from` 설비)을 플랜트에서 제거(시뮬레이션). 센서가 돌아오면 모니터가 자동으로 해결 처리. 같은 원인을 쓰는 로봇 사건은 같이 닫힘.
- 상태 칩(`chipScope.ts`, 기본 `line`): 컨베이어를 뺀 모든 설비(34대). 로봇 3대는 규칙 엔진 판정, 나머지는 플랜트 모델 상태(`resolveStatus`, 설비 자체 센서가 보여주는 값과 같음). 센서가 하나도 없는 설비(랙·지그·격리함 6대)는 판정할 수 없어 정상에 넣지 않고 "센서 없음 6"으로 따로 표시. 호환되지 않는 새 유형은 일반 센서(`GENERIC`)가 붙어 센서 있는 설비로 셈.
- 확인한 것: 칠러 유량 저하 → 로봇 3대 사건 + 칩 주의 5·이상 1, 해결 처리 → 3건 자동 해결·칩 28/0/0, 수동 주입 0.78 → 해결 처리 → 정상, 새로고침 시 열린 사건 정리. 안 한 것: 규칙 엔진 판정은 로봇 3대 외 설비로 확장되지 않음(다른 설비의 경보는 칩에는 반영되지만 이벤트·이력은 생기지 않음).

## 훈련 모드 (훈련 탭, `lib/training.ts` + `TrainingView.tsx` + 지도 `training` 바인딩)
- **지도에서 푸는 방식**: 훈련 탭을 열면 지도는 전체 화면 그대로이고 문제는 오른쪽 카드에 있음. 고장은 `PlantOverview`의 `main.training`(TrainScene)으로만 전달돼 **플랜트 모델 복사본에만** 걸림. 공유 고장 저장소(`kfc.plantInjected.v1`)·이벤트·이력·상단 칩은 건드리지 않음(확인: 저장소 null, 칩 정상 28 유지).
- 문제가 시작되면 흐름 시뮬레이션을 초기화하고 전체 보기로 돌아감. 고장 난 설비는 실제로 느려지거나 서고(센서 값, 라인 막힘이 그대로 반영됨).
- **정답이 새지 않게**: 제출 전에는 상태가 `normal`이 아닌 모든 설비를 똑같은 "점검 필요"(주의 색) 표시로 통일(`statuses`는 가린 값, 흐름·센서에는 진짜 값 `trueStatuses` 사용). 설비를 누르면 `TrainCard`(센서, 연결만, 고장 이름과 상태 등급 없음). 센서 패널 머리의 주의/이상 배지는 센서가 보여주는 관측값이라 남김. 제출하면 진짜 상태가 색으로 드러나고 카메라가 원인 설비로 날아가며, 카드에 "이 설비의 고장"과 영향이 표시됨.
- 8개 문제(쉬움 2·보통 4·어려움 2), 4지선다, 힌트 3단계, 해설, 앱 Rule Engine 판정 비교는 그대로. 센서 목록은 "참고"로 접어 둠(태블릿·접근성용).
- 훈련 탭을 떠나면 선택과 흐름이 원래대로 돌아감. 훈련 진행(점수)은 탭을 오가도 유지(컴포넌트를 계속 마운트).
- 엔진 판정이 기준 0.5 미만이면 "판정하지 못했어요"로 표시(예: 보호가스 소진에서 로봇 03). 해설은 템플릿이고 AI 설명은 없음. 설비·고장·센서 값은 전부 가정.
- 확인한 것: 쉬움 문제(점검 표시 1대), 보통 칠러 문제(표시 6대, 전부 같은 주의 스타일, 로봇 01 선택 시 센서와 칠러 연결 표시), 제출 후 칠러 이상 표시·확대·고장 이름, 탭 이동 후 원상 복귀. 안 한 것: 힌트와 지도 강조 연결(4단계), 어려움 문제의 눈으로 확인, 터치, 클래식 지도(`?map=classic`)에서는 지도 훈련이 동작하지 않음.

## 센서 데모 (`plantSensors.ts`)
- 설비 카드에 "센서 (생성한 데모 값)" 섹션: 값, 정상(초록)·주의(노랑)·이상(분홍) 띠와 현재 위치, 최근 30초 추세선, 근거 등급(가정 / 보조 출처). 보조 출처인 값은 마우스를 올리면 무엇이 사양에서 온 것인지 보임(예: 칠러 ±0.5 °C, 용접 전원 정격 450 A, 프레스 정격 1,300 kN).
- 값 생성: 흐름 시뮬레이션의 부하(가공 중이면 전류·온도 상승, 프레스는 램 동작에 맞춰 힘), 고정된 의사 잡음, 주입한 시나리오(해당 센서가 주의·이상 구간으로 이동), 공급 손실(전원 → 전류·전압 0, 냉각 → 온도 주의, 공기·가스·집진 → 해당 압력·풍량 주의).
- 일관성: 모든 설비에 대해 (정상, 설비별 시나리오 전체, 공급 손실 전파) × (대기·가동)를 돌려 센서 판정이 설비 상태와 같은지 확인함(5,760건, 불일치 0). 이 테스트는 레포에 넣지 않았음(TS를 임시로 변환해 Node에서 실행).
- 센서 범위와 공칭값은 거의 전부 가정. 적치·지그·격리함에는 센서를 두지 않음.

## 자재 흐름 시뮬레이션 (`plantSim.ts`)
- 프로필의 `flow`(시작: 자재 랙)를 따라 캐리어(토트)가 이동. 각 구간의 `route_m`은 출구 포트에서 입구 포트까지 통로를 따라가는 경로(설비를 관통하지 않음). 컨베이어 구간은 벨트 위, `cart`·`manual` 구간은 **자율 이송 카트(AMR) 위에 실려** 이동하는 것으로 그림(사람이 미는 대차가 아니라 AMR이라는 것은 가정). 설비가 부품을 안으로 받는 디버링·세척·검사·마킹은 처리 중 캐리어를 숨김. 택트(22.95 s)마다 하나씩 투입, 대기열이 쌓이면 투입 중단(WIP 최대 44).
- 설비는 한 번에 한 개만 처리하고, 처리 시간은 `cycleOf`로 파생된 사이클. 픽스처·포지셔너는 옆 로봇의 사이클을 씀. 이송 속도(컨베이어 0.25, 대차 0.8, 수동 0.6 m/s), 캐리어 간격 0.62 m는 **가정**.
- 상태 연동: 주의 = 속도 60%, 이상 = 정지(앞쪽에 대기열이 쌓임), 이상 컨베이어는 위의 캐리어를 멈춤. 전원 손실은 전부 정지.
- UI: 좌하단 재생/일시정지, 1×·10×·30×·60×, 흐름 초기화, 경과·완료·진행 중·최근 10분 기준 시간당 생산, 설비 카드의 처리 수·대기·가동률.
- **자재 랙·출하 재고 (모든 수치는 가정)**: 원자재 랙은 40개로 시작해 캐리어를 투입할 때마다 1개 줄고, 16개 이하가 되면 왼쪽 AGV(`agv_01`)가 입고 재고에서 24개 팔레트를 싣고 와 랙에 내려 채운다. 완성된 상자는 포장 설비 옆 팔레트에 쌓이고, 8개가 되면 오른쪽 AGV(`agv_02`)가 출하 재고로 옮긴다. 출하 재고는 팔레트 자리 6개(8개씩)이고 가득 찬 뒤 다음 팔레트가 오면 트럭이 가져간 것으로 비운다. 입고 재고는 무한 공급으로 둠. 항상 `완료 = 포장 대기 + 운반 중 + 출하 재고 + 출하`, `투입 = 40 + 보충 횟수 × 24 − 랙 잔량`이 성립한다(1×로 12,000 s, 60×로 3,000 s 시뮬레이션에서 위반 0). AGV는 라인 배속과 같이 움직여 어떤 배속에서도 랙이 마르지 않는다. AGV가 이상이면 멈춰 서고 랙이 비면 라인이 "원자재 대기"로 멈춘다(AGV 정지 후 복구 시험으로 확인). 주의는 60% 속도. 화면 좌하단 흐름 줄에 `원자재 / 포장 대기 / 출하 재고 / 출하`가 표시된다.
- 확인: 정상 상태에서 시간당 156개(택트 기준 157), 세척기 펌프 고장 주입 시 최근 10분 생산 0, 로봇이 픽스처의 캐리어 위에서 움직임(스핀들·토치·스캐너 효과), 프레스 램·레이저 판재·포지셔너 동작은 코드로 구현했고 화면으로는 레이저·프레스 램 동작을 따로 캡처하지 않음.
- 한계: 품질 불량·재작업·교대·작업자 없음(자재 소진은 AGV 정지 때만 발생). 실제 라인의 병렬 처리(터널 세척기 다수 투입)는 단순화. 가동률은 시뮬 시작부터 누적이라 초반에 낮게 보임.

## 라인 공통 높이와 이송 접점 (`machinePaths.ts`의 `BELT_TOP`)
- 문제: 설비마다 벨트·테이블 높이가 달랐다(컨베이어 윗면 0.585, 설비 벨트 0.68~0.69, 카트 갑판 0.41, 포지셔너 1.04 m). 그래서 트레이가 카트에서 벨트로 "올라가거나" 벨트 안으로 5 cm쯤 파묻혔다.
- 해결: 모든 벨트·롤러 베드·턴테이블 판·카트 갑판의 윗면을 **0.68 m(예시 값)** 한 곳(`BELT_TOP`)에서 정하고, 트레이 바닥이 그 위에 놓이게 캐리어 높이를 `ON_BELT`(= 0.68 + 0.104)로 통일했다. 시뮬레이션의 모든 설비에서 캐리어 높이가 0.784로 나온다(예외: 레이저 선반 1.185, 레이저 램프 위).
- 이송 카트는 롤러 갑판을 **리프트 기둥(벨로스)** 위에 올려 벨트 높이에 맞춘다(`AgvDetail`의 `lift`, `CART_LIFT`). 카트는 벨트 밑이 아니라 **벨트 끝 옆**에 선다(겹치지 않게 입구 포트 위치를 옮김: 디버링 22.6, 프레스 z 8.3·12.7, 레이저 z 9.7). 레이저 램프는 길이 0.67 → 1.1 m로 늘려 경사를 31°에서 20°로 낮췄다.
- 컨베이어(h 0.62 → 0.715)는 포지셔너·검사·마킹 구간에서 **끊어서** 그린다(`beltGap`, `conveyorPieces`): 설비가 자기 벨트를 가진 곳에서 벨트 두 개가 겹치지 않게.
- 포지셔너는 판 두 개(±0.65 m)를 벨트 높이로 내렸다. 트레이는 입구 판(x−0.65)에 올라 용접을 받고, 작업 끝에 테이블이 반 바퀴 돌면서(`positionerTurn`) 출구 판(x+0.65)으로 옮겨진다. 로봇 03·컨트롤러는 입구 판 앞(x 39.55)으로 옮겼다(같은 자리에서 팔이 닿지 않았음: 닿지 못한 프레임 25% → 재확인 필요).
- 집진 덕트는 흄 후드의 둥근 출구 플랜지 끝에서 끝난다(`HOOD_OUTLET`). 덕트 반지름은 0.07 → 0.1 m(집진기 입구 스텁과 같은 크기).
- 용접 시 이음 자국(`Robot`의 `bead`)이 토치를 따라 자라고 끝에 달궈진 점이 따라간다: 로봇이 무엇을 하는지 보이게.
- 한계: 이것은 물리 엔진이 아니라 **한 높이를 정하고 접점마다 맞춘 것**이다(충돌·중력·미끄러짐 계산 없음). 새 설비를 넣을 때는 벨트 윗면을 `BELT_TOP`에 맞춰야 한다.
